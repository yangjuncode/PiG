agent loop：一台事件驱动的状态机

agent/agent_loop.go 只有 548 行，但它是整个 coding agent 的心脏。读懂这一页，你就拿到了写自己 agent 的完整模板：一个 turn 是什么、循环何时停、错误和取消怎么走、工具并发怎么保序。

1全景：run 的生命周期

一切从四个入口收敛到 runLoop：Send / SendContent / SendMessages（新 prompt）和 Continue（不重发 prompt 的续跑，比如压缩后重试）。调用链：

Send(ctx, text)
  └─ BeginSendContent          ← beginRun: 占用 agent（streaming=true），
     │                            挂上 runContext/runCancel/runDone
     └─ PromptRun.Run()
        └─ runLoop(ctx, cfg, prompts)
           ├─ emit(AgentStartEvent) + TurnStartEvent
           ├─ prompt 消息各发一对 MessageStart/MessageEnd
           └─ run.loop()        ← 本课的主角
        finishRun()            ← 释放占用，close(runDone)

三个不变量，记住它们后面所有细节都有处安放：

  • 一个 agent 同时只有一个 run。beginRun 是占用锁，重入直接返回 ErrAlreadyProcessing。
  • 事件是唯一出口。引擎不认识 UI、持久化、扩展——它们都是 emit() 管线下游的订阅者。
  • message_end 才是提交点。消息在流式期间是"私有草稿"，只有 MessageEndEvent 会写进公开 transcript（emit 里 appendMessages）并触发 OnMessagePersist 落盘。

2双层循环：loop() 逐段读

loopRun.loop()（agent_loop.go:151）是两层循环：内层消化"还要继续干活"的信号（工具调用、steering 插话），外层消化"整轮结束后再来一轮"的信号（follow-up 队列、扩展请求的显式续跑）。

pendingMessages ← steeringQueue.Drain()        // 运行期间用户插的话
for {                                          // ── 外层：follow-up / 显式续跑
  hasMoreToolCalls := true
  for hasMoreToolCalls || len(pendingMessages) > 0 {   // ── 内层：turn 循环
    if turnIndex >= MaxTurns { endRun; return ErrMaxTurnsReached }
    refreshModel()                             // SetModel 即时生效
    if lastCompletedTurn != nil {
      prepared ← prepareNextTurn(turn)         // 可换 context/model/thinking
      pending  ← steeringQueue.Drain()         // 压缩可能很慢，顺手再收一次插话
      emit(TurnStartEvent)
    }
    appendMessage(declareToolChanges(...))     // 工具集变化也落成消息
    prepareRequest()                           // 每次请求前的改写钩子
    turn, done, err ← runTurn()                // ← 下一节
    if done { return err }                     // 硬退出：error/aborted
    if decision == AgentTurnEnd { endRun; return nil }
    hasMoreToolCalls ← turn.hasMoreToolCalls
    pendingMessages ← steeringQueue.Drain()
  }
  if followUps ← followUpQueue.Drain(); 非空 { pending = followUps; continue }
  if explicitContinuation { continue }         // FinishTurn 要的"再来一轮"
  break
}
endRun()   // emit(AgentEndEvent{newMessages})
读法提示 loop() 本质是状态机，hasMoreToolCalls 和 pendingMessages 是两个"继续条件"。想清楚每次迭代末尾这两个值怎么被重算，整个循环就没有秘密了。

3runTurn：一个 turn = 流式响应 + 工具批 + 决策钩子

runTurn()（agent_loop.go:241）返回 (completedTurn, done, error)。三元组各管一件事：本轮产出、run 是否已终结、有无错误。流程：

assistant, toolCalls, err ← streamAssistantResponse()
├─ err            → append + finishTurn + turnEnd + endRun → done=true
├─ stopReason ∈ {error, aborted} → 同上，但 err=nil（决策钩子被跳过）
└─ 正常：
   ├─ len(toolCalls) > 0:
   │   ├─ stopReason == length → failToolCallsFromTruncatedMessage
   │   │     （输出被截断 ⇒ 参数可能不完整 ⇒ 整批拒绝执行）
   │   └─ 否则 → executeToolCalls（见下节）
   ├─ decision ← finishTurn(turnContext)   // 扩展可判 continue/end
   └─ emitTurnEnd

stopReason 是控制流的开关，四个值四种走法：

stopReason含义循环动作
stop模型正常说完无工具调用 → 内层循环自然退出
toolUse响应里有工具调用执行工具批 → hasMoreToolCalls=true → 再跑一 turn
aborted / error取消或失败硬退出：跳过决策钩子，直接 endRun
length撞到输出上限工具调用全部标记失败再进入下一 turn（防止执行截断参数）
旁注：length 的处理是个值得抄的细节——流式协议下"截断的 JSON 参数"可能侥幸 parse 成功，静默执行半个参数比报错危险得多。

4工具批：prepare 串行 / execute 并发 / result 保序

一条 assistant 消息可能带多个工具调用。executeToolCalls（tool_execution.go:51）默认并发，但分三段，每段的顺序语义不同：

阶段顺序为什么
prepare（emit start、查工具、校验参数、BeforeToolCall 钩子） 严格按源序串行 复刻上游 Promise.all(calls.map(...)) 的同步前缀：tool_execution_start 事件顺序、QueueOrderable 的文件变更票据，都必须按调用顺序签发——goroutine 自己保证不了
execute（tool.Execute(ctx, id, args, onUpdate)） wg.Go 全并发 = Promise.all。刻意不加 CPU 数上限：工具是 IO 密集的
finalize（emit end、写 toolResult 消息） end 事件按完成序，transcript 按源序 事件忠实反映谁先跑完；但消息历史必须稳定可重现

单个调用内部还有一条钩子管线：findTool → PrepareArguments → schema 校验 → BeforeToolCall（可拦截/改参数）→ Execute（onUpdate 流式进度）→ AfterToolCall（可改结果）→ PrepareToolResult → appendToolResult。工具 panic 会被 recover 成 error result——一个坏工具炸不掉整个 run。

5emit() 管线：事件的单出口

所有事件（agent.go:1544）走同一条管线，顺序即契约：

emit(ev):
  1. MessageEndEvent → appendMessages     ← 提交到公开 transcript（唯一提交点）
  2. reduceEventState                     ← 更新 streamingMessage / pendingToolCalls
  3. notifyListeners                      ← 按订阅序同步调用；返回 error → panic(runFailure)
  4. OnEvent                              ← 可原地替换消息（扩展点）
  5. MessageEndEvent → persistMessage     ← OnMessagePersist 落盘
  6. EventCh / EventDone                  ← 非阻塞 channel 投递（EventDone 关闭后丢弃）
  7. AfterEvent                           ← 返回 error → panic(runFailure)
两个移植味很浓的决策 同步 listener：上游 TS 会 await 每个 listener，所以 Go 版也是同步调用——listener 的错误经 panic(runFailure) 传到 catchRunFailure，再走 handleRunFailure 合成一条完整的失败生命周期（error 消息 + turn_end + agent_end），而不是把 run 半截扔在那。

provider 失败不 throw：requestStream 把"请求没建起来"合成为一条 stopReason=error 的 assistant 消息走正常生命周期——这样上层重试逻辑收到的是可分类的数据（rate limit？网络？），不是一根炸断的调用栈。

6三条"消息插队"通道

run 在跑的时候外界还能往里塞消息，三条通道语义不同：

通道API何时被消费典型用途
steering queuea.Steer(msg)当前工具批结束后、下一次模型调用前用户中途改主意："别改那个文件了"
follow-up queuea.FollowUp(msg)整轮 run 收尾时（外层循环）"做完这个再帮我跑下测试"
next-turn 槽a.QueueNextTurn(msg)下一次 Send 时贴在用户消息旁扩展想给下一个 prompt 提供上下文

两条队列各有 QueueModeAll / QueueModeOneAtATime 两种 drain 策略（默认一次一条）。QueueNextTurn 不是队列：run 闲着时没有 goroutine 会 drain 它，所以它跟着下一次 prompt 走。

7retrieval practice

Q1 · 仅当 MessageEndEvent 经过 emit() 时才发生的两件事是？

其余三件对所有事件都发生；占用释放只在 finishRun。message_end 是唯一的"提交点"——流式期间的草稿不进 transcript、不落盘。

Q2 · 模型返回 stopReason=length 且消息里带工具调用，循环会？

截断的 JSON 可能侥幸解析成功——执行"半个参数"比报错危险。failToolCallsFromTruncatedMessage 给每个调用一条说明性错误结果，让模型下一轮自己重发完整调用。

Q3 · 并行工具批里，prepare 阶段为什么仍按源序串行？

复刻 Promise.all(map) 的同步前缀语义：tool_execution_start 顺序、QueueOrderable 文件票据都依赖调用顺序。goroutine 调度顺序是runtime说了算，必须用串行循环兜底。

Q4 · Steer 和 FollowUp 的区别是？

steering 在内层循环的每轮迭代开头被 drain，能改变"下一次模型调用"看到的东西；follow-up 只在外层循环、run 本来要结束时才被看。两条队列的 drain 策略都可配（all / one-at-a-time），所以 D 不对。

Q5 · provider 在流式开始前就失败（如网络错误），run 会？

requestStream 合成 stopReason=error 的 assistant 消息并走 message_start/end——上层（如 codingagent 的重试逻辑）拿到的是可分类的结构化结果；transcript 里也留下了一致的失败记录。

Q6 · 读一遍 loop()（agent_loop.go:151）：它一共有几种退出路径？

break=自然结束；return nil=决策钩子判 end 或 prepareNextTurn 失败已入账；return err=runTurn 硬退出或 MaxTurns 触顶（ErrMaxTurnsReached 是 error）。注意 prepareNextTurn 失败 return nil——失败已合成进消息，不算 run 的错误。

9对你自己 agent 的可抄清单

设计要不要抄理由
事件单出口 + message_end 提交点抄UI/持久化/日志全是订阅者，引擎零依赖；提交点唯一则一致性永远简单
stopReason 驱动控制流抄四值开关比一堆 bool 标志干净；length→整批拒执行是真实踩坑经验
工具批三段式（串行 prepare / 并发 execute / 源序 finalize）抄并发提速但不牺牲事件序与 transcript 确定性
provider 失败合成 error 消息抄让重试策略处理数据而不是异常；transcript 自洽
两条队列 + next-turn 槽按需你的 agent 若不需要"中途插话"，一条队列就够
panic(runFailure) 传 listener 错误三思这是"把 TS throw 翻译成 Go"的产物；从零写可用显式 error 链
runDeadlineContext 取消解耦三思同样是对齐 Pi 的 AbortSignal 语义；简单 agent 直接 ctx 取消即可
